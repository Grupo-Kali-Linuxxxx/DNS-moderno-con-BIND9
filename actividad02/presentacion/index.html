⚠️ Contexto del Problema: De 'hosts' a un DNS Corporativo

La red escolar de la Unidad Educativa Horizonte creció a más de 40 terminales, impresoras y servicios web/correo.

❌ El Pasado: Archivo 'hosts'

  • Cada máquina mantenía su propia lista estática manual.
  • Inmanejable con más de 10 dispositivos.
  • Cualquier cambio de IP requería modificar 40 computadoras una a una.
  • Peligro constante de suplantación y desincronización.

✅ La Solución: BIND 9.18 + Unbound

  • Autonomía y Alta Disponibilidad: Servidor primario (ns1) y secundario (ns2).
  • Seguridad Criptográfica: Transferencias restringidas mediante claves TSIG.
  • Resolución Cifrada (DoT): El ISP no puede espiar el tráfico en el puerto 853.
  • Filtrado RPZ: Bloqueo de sitios de apuestas y redirección de phishing escolar.

🌍 Jerarquía DNS y Resolución Iterativa

El estándar DNS resuelve nombres mediante delegaciones sucesivas de arriba hacia abajo (demostrado con dig +trace):

1. Zona Raíz [ . ]

13 clústeres de servidores mundiales (a.root-servers.net hasta m.root-servers.net). Responden con referencias al TLD correspondiente.

h.root-servers.net -> 32 ms

2. Servidores TLD [ .bo ]

Administran el registro de primer nivel de cada país (operado por ADSIB/NIC Bolivia). Delegan hacia los servidores de la institución.

ns.nic.bo -> 64 ms

3. Autoritativos [ horizonte ]

Custodian la verdad oficial de la zona escolar (ns1 y ns2). Entregan la IP autoritativa del host web final.

ns1.horizonte.internal -> 0 ms

🔍 Diferencia Crítica: Un autoritativo (BIND9) sabe la verdad de su propia zona; un recursor (Unbound) viaja por todo internet para responder a las PCs cliente.

⏱️ Justificación Técnica: Temporizadores y Serial SOA

Los parámetros temporales del SOA determinan la resiliencia y el comportamiento del caché de la escuela:

🔢 Formato del Serial: AAAAMMDDnn

Se configuró 2026100701. Garantiza monotonicidad matemática estricta. Si se olvida subir el serial, el secundario rechaza actualizarse aunque reciba NOTIFY.

⚡ TTL por Defecto: 3600s (1 Hora)

Permite un equilibrio óptimo: descongestiona la red con caché y asegura que cualquier contingencia de IPs se propague en menos de 60 minutos.

🛡️ Temporizadores de Resiliencia

  • Refresh (3600s): ns2 comprueba si hay cambios en ns1 cada hora.
  • Retry (600s): Reintento cada 10 minutos si ns1 no responde.
  • Expire (14 días): Si ns1 muere, ns2 sigue atendiendo 2 semanas completas antes de apagarse.
  • Negative TTL (300s): Evita que dominios inexistentes queden bloqueados en caché más de 5 min.

⚙️ Configuración del Primario (ns1) y Zona Inversa

Endurecimiento perimetral en named.conf.options y zonas inversas canónicas:

Seguridad en ns1 (named.conf.options)

options {
    directory "/var/cache/bind";
    recursion no;            // ¡Sin amplificación DDoS!
    allow-query { any; };
    allow-transfer { none; };// Cero fugas de zona
    version "no disponible"; // Oculta versión
};

Zona Inversa (db.10.10.10)

; Regla de oro: FQDN con punto final
20  IN  PTR www.horizonte.internal.
25  IN  PTR mail.horizonte.internal.
; Sin punto final, BIND concatenaría:
; mail.horizonte.internal.10.10.10.in-addr.arpa.

✅ Validación: Ambos archivos validados con named-checkconf y named-checkzone con estado OK.

🔐 Servidor Secundario (ns2) y Firma TSIG (RFC 2845)

La transferencia de zona completa (AXFR) está blindada criptográficamente con clave simétrica:

🛡️ ¿Por qué TSIG y no control por IP?

  • La restricción por IP es vulnerable a IP Spoofing en capa 2.
  • TSIG usa HMAC-SHA256: Firma el paquete completo con un secreto compartido y marca de tiempo (timestamp).
  • Imposible de falsificar o reutilizar en ataques de repetición.

⚡ Demostración de Seguridad

# 1. Consulta SIN clave TSIG:
$ dig @10.10.10.2 horizonte.internal AXFR
; Transfer failed.  [RECHAZADO]

# 2. Consulta CON clave TSIG:
$ dig -k transferencia.key @10.10.10.2 AXFR
transferencia-horizonte. TSIG NOERROR
XFR size: 17 records [EXITOSO]

🛡️ Capa de Perímetro: Unbound, DoT y Filtrado RPZ

El nodo resolutor (10.10.10.4) protege la navegación de toda la comunidad educativa:

🔒 DoT (Puerto 853)

Consultas externas hacia Cloudflare y Quad9 cifradas con TLS. Cero paquetes por el puerto 53 (demostrado con tcpdump).

🚫 Filtro RPZ

Bloqueo de sitios de apuestas (NXDOMAIN) y redirección de phishing (horizonte-notas-login.com a 10.10.10.20).

⚡ Aceleración Caché

Primera consulta en 1131 ms; segunda consulta en 0 ms desde memoria RAM con validación DNSSEC activa.

📊 Comparativa: BIND9 (Linux) vs Windows Server DNS

Criterio BIND9 / Unbound en Linux Windows Server DNS (Active Directory)
Almacenamiento Archivos de texto estándar (/var/lib/bind) Integrado en la base de datos de AD (NTDS.DIT)
Replicación NOTIFY + AXFR/IXFR firmados con TSIG Replicación multimaster por RPC / DRA
Filtrado Response Policy Zones (RPZ estándar RFC) DNS Policies de PowerShell / GPO
Cifrado DoT Nativo con Unbound en puerto 853 Soporte DoH a partir de Windows Server 2022
Costo $0 USD (Open Source sin licencias) Costo por licencia de Windows Server + CALs
